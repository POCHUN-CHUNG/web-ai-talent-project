## 三、X · 文件 ↔ 程式碼 不一致

### X-01 **[阻斷]** 無風險利率 $R_f$：抓了卻不用

| 面向 | 內容 |
| --- | --- |
| D1 | n8n 每日爬取「五大公股銀行 1 年期定存機動利率」作為無風險利率 $R_f$ 基準 |
| C1/C4 | 已實作 `BankRate` 資料表、抓取服務與 n8n 排程，每次存入 5 筆 |
| D2 §2.5 | **明定 $R_f = 0\%$**、$MAR = 0\%$，Sharpe $= R_p/\sigma_p$、Sortino $= R_p/DD$ |

兩者直接衝突：若 $R_f$ 固定為 0，整條銀行利率管線在風險指標上**沒有任何用途**。
→ 見 Q-01。

### X-02 n8n 工作流程與後端回傳格式已脫鉤（2026-09-20 複查，仍存在）

| 面向 | 內容 |
| --- | --- |
| C1 `bank_rates.py` 現況 | 回傳 `{"status": "成功", "message": str, "rates": [{"bank","name","rate"}]}` |
| C4 n8n Email 節點 | 讀取 `$json.taiwan_bank`、`$json.tcb_bank` …（扁平結構） |

匯出的 workflow JSON 仍是更早版本的扁平格式，現況執行會取到 `undefined`。
修正方向二選一：改 n8n 運算式為 `$json.rates[0].rate` 之類的陣列存取，或在後端額外回傳一組扁平欄位。建議前者——後端回傳格式不該為了下游的顯示方便而重複。

### X-03 n8n Email 平均利率計算式錯誤

C4 的算式為 `(5 家加總) / 2`，分母應為 `5`。目前信件中的「平均利率」約為實際值的 2.5 倍。

### X-04 n8n 排程週期未設定

C4 `scheduleTrigger` 的 `rule.interval` 為 `[{}]`（空物件，套用 n8n 預設），與 D1「每日爬取」不構成明確對應。SPEC 需寫死 cron 與時區。→ 見 Q-02。

### X-05 CORS 與前端 API 客戶端只支援 GET / POST

| 面向 | 內容 |
| --- | --- |
| C1 `main.py` | `allow_methods=["GET", "POST"]` |
| C2 `api.ts` | 有 body 即 POST、無 body 即 GET，**無法送出 PUT／PATCH／DELETE** |
| D1 Step 3 | 投資組合需可新增持股；一般也需修改與刪除 |

投資組合 CRUD 落地時必然撞到這個限制。→ 見 Q-08。

### X-06 密碼強度規則與一般安全預期落差

C1 `auth.py`：`password` 為 `min_length=1`、`pattern=^[A-Za-z0-9]+$`。即單一字元 `a` 可註冊成功，且不允許符號。
C5 `CLAUDE.md` 雖聲明「開發階段、測試資料、無資安疑慮」，但 SPEC §5.1 必須寫下最終規則。→ 見 Q-09。

### N-02 決策建議（$MAR$ 是否改用 $R_f$）

**建議採 MAR = $R_f$，並將下行波動度公式改寫為 $DD=\sqrt{\frac1n\sum \min(R_{p,t}-R_{f,daily},\,0)^2}$。**

理由：

1. **定義自洽**：Sortino 的原始定義要求分子的目標報酬與分母的下行門檻是同一個值。分子用 $R_f$、分母用 0，是文獻上已知的常見誤用，口試或審閱時是可被直接指摘的點。
2. **這套系統的設計前提需要它**：D2 §5.4 規定「由 Skewness 決定優先看 Sharpe 還是 Sortino」。這個設計成立的前提是兩者衡量的是同一件事、只是風險定義不同。若分子基準不同，AI 在兩者之間切換時的敘述會失真。
3. **數值代價近乎為零**：台灣 1 年期定存機動利率約 1.5%～1.8%，日化後約 0.006%／日。門檻位移極小，$DD$ 與 Sortino 的變化通常在 1% 以內，但換來定義上的完整。
4. **代價只在文件**：D2 §6 的 $\min(R_t,0)$ 公式需改寫，屬規格修訂，不是實作成本。

保留 MAR = 0% 的唯一合理情境：刻意把 Sortino 定位成「本金保全視角」（任何虧損都算風險，定存報酬不是及格線）。若採此路線，SPEC 必須明寫「本系統的 Sharpe 與 Sortino 基準不同，兩者的數值不可互相換算」，且 AI Prompt 需禁止把兩者當成同一尺度比較。
